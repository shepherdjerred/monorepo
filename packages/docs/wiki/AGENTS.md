# Human wiki authoring

`packages/docs/wiki/` is Jerred's human-first explanation layer. AI agents
author it, but Jerred is the reader.

The wiki follows [Diátaxis](https://diataxis.fr/). **Load the `diataxis` skill
before writing here.** This file covers what is specific to this wiki; the skill
covers the framework.

## The one rule

**A page is exactly one kind of documentation.** Not two. If a page teaches,
instructs, describes, and discusses, it fails at all four.

Use the compass to decide which kind you are writing:

| Informs   | Serves      | Directory      | Sidebar       |
| --------- | ----------- | -------------- | ------------- |
| action    | acquisition | `tutorials/`   | Tutorials     |
| action    | application | `how-to/`      | How-to guides |
| cognition | application | `reference/`   | Reference     |
| cognition | acquisition | `explanation/` | Concepts      |

If a paragraph answers a different question than the page it is in, move it and
link to it. That relocation is the single highest-value edit in this wiki.

## Structure

```text
src/content/docs/
├── index.md          # splash; routes by reader need
├── tutorials/        # flat
├── how-to/           # flat
├── reference/        # flat
└── explanation/      # nested one level by subject (homelab/, temporal/, …)
```

- Files are kebab-case, named for the reader's goal — `cut-a-homelab-release`,
  not `releases`. Subject lives in the slug, not in a directory, except under
  `explanation/` where the page count justifies one level of nesting.
- The sidebar is **autogenerated** from these directories. Set `sidebar.order`
  in frontmatter to place a page. Never hand-add a link to `astro.config.ts`;
  a page that exists is a page in the nav.
- Frontmatter needs `title` and `description`. No custom kind field — the
  directory is the kind. No Markdown H1; Starlight renders the title.
- Use absolute wiki routes (`/how-to/cut-a-homelab-release/`).

## What each kind looks like here

**Tutorials** — rare, and that is correct: the reader owns these systems and is
seldom a novice in them. Write one only when there is a genuine end-to-end
lesson with a real finish line. Never pad the section.

**How-to guides** — the operational core. One orienting sentence, numbered
steps, tables for facts, an aside for a trap, `## Related` at the end. Assume
competence. Link out instead of teaching. Troubleshooting pages live here and
are titled `How to diagnose …`.

**Reference** — tables, not prose. Every flag, path, port, schedule, timeout,
and permission in this wiki belongs on exactly one reference page, and
everything else links to it.

**Explanation** — where this wiki is strongest. Say _why_: the constraint, the
decision, the alternative rejected. Opinion belongs here. The moment you list
flags or steps you are in the wrong kind. Diagrams live here.

## Voice and prose

- Open with a one-sentence answer. Then a short summary. Then sections.
- One idea per sentence, under ~25 words, at most one subordinate clause. A
  sentence with two em-dash asides is three sentences.
- Bullets are parallel items, not paragraph containers. Cap ~40 words; longer
  wants to be a subsection.
- Be terse and concrete: real names, paths, commands, current boundaries.
- Explain intent and tradeoffs. Never narrate a directory tree.
- Every claim about the system links the source file that proves it.

## Hard exclusions

- **No workflow or plan residue.** No "superseded", no "the deep-dive plan
  remains in progress", no "this TODO stays open", no status. That is
  agent-to-agent state and belongs in `packages/docs/`.
- **No secrets or private data.** This site is public: no tokens, private host
  details, personal data, or sensitive incident material.
- **No duplicated facts.** State something once; link to it everywhere else.
- **No FAQ pages.**

## Diagrams and images

- Use Mermaid when relationships, flow, ownership, or lifecycle scan better
  visually. Every block needs `accTitle` and `accDescr`.
- Keep diagrams readable without zooming; split dense ones.
- Screenshots for real UI, dashboards, and rendered output. Useful alt text,
  cropped to the evidence. Store durable images in `src/assets/` and use Astro
  image paths. Do not hotlink ephemeral screenshots.
- Do not add a diagram when a sentence is clearer.

## Working material

`/working/` is provenance, not documentation, and sits outside the four kinds.

- Only paths listed in `src/lib/wiki-publication.ts` render under `/working/`.
- Approved working pages carry a banner, are hidden from the sidebar and
  sitemap, are `noindex,follow`, and are down-ranked in Pagefind.
- To publish one, review it for public-data safety, then add its
  `packages/docs/`-relative path to that allowlist. Never copy a working
  document into the curated wiki.

## Keeping it current

When a change alters a meaningful system boundary, operator workflow, or
architectural reason, update the nearest page in the same change — in the
_right kind_ of page. A new flag is a reference edit, not a rewrite of an
explanation page. Routine refactors need no wiki churn.

Prefer updating an existing page over creating a near-duplicate.
