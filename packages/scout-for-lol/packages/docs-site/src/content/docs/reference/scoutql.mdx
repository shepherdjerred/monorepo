ScoutQL is the language reports and Explore are written in. It is a bounded
subset of [DuckDB](https://duckdb.org/docs/stable/sql/introduction) SQL over
Scout's match data, plus a trailing `RENDER` clause and four Scout-specific
calls (`player`, `champion`, `kda`, `per_minute`).

Where ScoutQL overlaps SQL it means exactly what DuckDB means. There are no
conveniences layered on top: `AVG(win)` is an error in DuckDB and an error
here, aggregates are always written out, and a name in `WITH (...)` has to be a
name the `SELECT` produced.

## Report ScoutQL and contract ScoutQL

The editor syntax documented on this page is report ScoutQL: one bounded data
source plus grouping, aggregation, ordering, and rendering. Dare v2 contracts
use a relational profile of ScoutQL with qualified columns, aliases,
non-recursive CTEs, bounded joins, scalar subqueries, and deterministic first-N
game sets. Explore can parse, validate, and canonically format that profile
without executing it; the contract authoring tools generate the query and its
typed evaluator plan together.

Contract ScoutQL always returns exactly one nullable Boolean named `achieved`:
`true` means proven, `false` means conclusively not achieved, and `null` means
the bounded evidence is insufficient. Its compiler accepts only the closed
match and timeline catalog, freezes every `dare_target('Tn')` binding at
funding, parameterizes values, and rejects wall-clock or dynamic player
resolution. Validation first serializes the DuckDB AST, then applies Scout's
closed-world source, function, target, statement, and complexity policy. A
successful compilation returns canonical text plus the hash of its immutable
AST; it never runs the submitted query. The ordinary report editor does not
accept this relational profile; inspect and revise contracts through Explore.

This separation is deliberate. A contract must remain reproducible after a
player rename, prompt change, or compiler upgrade, while an interactive report
is allowed to resolve today's player aliases and render rows for exploration.

## Clause order

```text
SELECT   <expression> [AS <name>] [, …]     -- 1 to 20 outputs
FROM     <source>
[WHERE   <predicate>]
[GROUP BY ALL | <expression> [, …]]         -- up to 3
[HAVING  <predicate>]
[ORDER BY <key> [ASC | DESC] [, …]]         -- up to 3
[LIMIT   <n>]
[RENDER  <kind> [WITH (<option> = <value>, …)]]
```

`SELECT` and `FROM` are the only required clauses. A query with no `GROUP BY`
returns one grand-total row; a query with no `RENDER` renders as a table.

Keywords are case-insensitive. String values are not — they are compared
exactly, as DuckDB compares them.

## Comments

`--` comments run to the end of the line and may appear anywhere.

```scoutql
-- Ranked solo activity, last four weeks.
SELECT COUNT(*) AS games
FROM match_participants
WHERE queue = 'solo' -- ARAM and Arena excluded
  AND game_creation_at >= CURRENT_TIMESTAMP - INTERVAL 28 DAY
GROUP BY player
ORDER BY games DESC
```

## Outputs are named, and the name is the handle

Every computed output takes an `AS` name. That name is what `HAVING`,
`ORDER BY`, and `WITH (...)` refer to, what a table column is headed with, and
what a chart series is labelled with.

```scoutql
SELECT COUNT(*) AS games, AVG(win::INT) AS win_rate
FROM match_participants
WHERE game_creation_at >= CURRENT_TIMESTAMP - INTERVAL 30 DAY
GROUP BY player
HAVING games >= 10
ORDER BY win_rate DESC
RENDER bar_chart WITH (y = win_rate)
```

## WHERE filters rows; HAVING filters groups

`WHERE` is a full boolean expression over the source's columns — `AND`, `OR`,
`NOT`, and parentheses — evaluated before rows are collapsed. `HAVING` is a
boolean expression over the aggregates, evaluated after, and may name the
aliases the `SELECT` defined.

An aggregate in `WHERE` is rejected rather than reinterpreted, because a
minimum-games floor written there would silently filter individual games
instead of players.

```scoutql
SELECT COUNT(*) AS games, AVG(win::INT) AS win_rate
FROM match_participants
WHERE (queue = 'solo' OR queue = 'flex')
  AND NOT early_surrendered
  AND game_creation_at >= CURRENT_TIMESTAMP - INTERVAL 90 DAY
GROUP BY player
HAVING games >= 20 AND win_rate > 0.5
ORDER BY win_rate DESC
```

## Time bounds are ordinary WHERE conditions

There is no time clause. A window is a comparison against the source's own
timestamp column, joined into `WHERE` with `AND` like any other condition. The
compiler recognizes the shapes below and executes them as the query's window;
anything else is applied as a plain filter.

Relative — a rolling window ending now:

```scoutql
SELECT COUNT(*) AS games
FROM match_participants
WHERE game_creation_at >= CURRENT_TIMESTAMP - INTERVAL 30 DAY
GROUP BY player
```

Calendar — whole days, in a named zone, both ends inclusive:

```scoutql
SELECT COUNT(*) AS games
FROM match_participants
WHERE (game_creation_at AT TIME ZONE 'America/Los_Angeles')::DATE
  BETWEEN '2026-01-01' AND '2026-01-31'
GROUP BY player
```

A calendar bound compares dates, not instants, so the zone has to be stated
before the cast: "January" starts at a different moment in Los Angeles than in
Berlin, and without `AT TIME ZONE` the days are UTC days.

Each source names the column its window is measured on — see
[Sources and columns](/docs/reference/scoutql-sources/). The rank snapshot
sources have no timestamp column at all: a snapshot is current by construction,
so there is nothing to bound.

### Omitting the bound

A query with no time condition is legal and covers **every match Scout has
ingested**. The editor flags it as a warning (`time-window-unbounded`) without
refusing it.

Both halves of that are deliberate. Refusing would make "how many games have we
ever played?" unaskable, and the query is measured — the whole lake is fast to
scan. But an unbounded answer read as though it covered the last month is
indistinguishable from a correct one, so the warning exists to make the choice
visible rather than accidental.

## Casts and strings

Strings are single-quoted, and a literal quote is doubled: `'Kai''Sa'`.
Double quotes are an error, because DuckDB reads them as identifiers and a
query that meant a value would silently ask for a column.

`::` casts, and it is required wherever DuckDB requires it — most often
`win::INT`, since a boolean has no average until it is a number.

Function names, interval units (`DAY`, `WEEK`, `MONTH`, `YEAR`),
`DATE_TRUNC` parts, render kinds, and render option names are **not** keywords.
They are ordinary identifiers resolved by meaning, which is why a column called
`day` or an output called `sort` causes no trouble.
