export const optionRows = SCOUTQL_CHART_OPTION_NAMES.map((name) => {
  const doc = OPTION_DOCS[name];
  if (doc === undefined) {
    throw new Error(
      `Undocumented ScoutQL render option "${name}" — add it to OPTION_DOCS in scoutql-render.mdx.`,
    );
  }
  return { name, syntax: doc[0], description: doc[1] };
});

The trailing `RENDER <kind> [WITH (…)]` clause decides how a result is
displayed. A query with no `RENDER` clause renders as a table.

`leaderboard` is the only kind that `@mention`s people, and it takes its own
option: `mentions = <n>` pings the top n ranked rows, `mentions = all` pings
every eligible row, and `mentions = 0` pings nobody. Omitted, it pings the top
three. Rows grouped by anything other than a player never mention anyone, even
when a champion name happens to match an alias.

Every name inside `WITH (…)` must be one of the query's own outputs or
groupings. A name the `SELECT` does not produce is rejected when the query
compiles rather than silently plotting nothing.

## What each kind needs

| Kind                       | Requires                                                         |
| -------------------------- | ---------------------------------------------------------------- |
| `bar_chart`, `stacked_bar` | `y`; optionally `orientation`                                    |
| `line_chart`, `area_chart` | `y`; a `DATE_TRUNC` grouping for a time axis                     |
| `donut_chart`              | exactly one `y`, and few rows                                    |
| `scatter_chart`            | one `x` and one `y`, both SELECTed; optionally `size`            |
| `heatmap`                  | `value`, `series`, and exactly two groupings                     |
| `radar_chart`              | three to eight `y` outputs over one grouping                     |
| `kpi_card`                 | no `GROUP BY` — one grand-total row                              |
| `bump_chart`               | one `y`, a `DATE_TRUNC` grouping, plus one more grouping to rank |
| `calendar_heatmap`         | one `y` and `DATE_TRUNC('day', …)` as the only grouping          |
| `histogram`                | one numeric bucket grouping and one count `y`                    |
| `box_plot`                 | exactly five `y` outputs — see below                             |
| `leaderboard`              | optionally `mentions`                                            |

## Comparing against the previous period

`compare = previous_period` re-runs the same aggregation over the equally long
span immediately before the query's window and overlays it, giving every point
a baseline, an absolute delta, and a percentage delta.

It needs two things, and says so if either is missing: a stated time window to
take the preceding period _of_, and a `DATE_TRUNC` (or `patch`) grouping to
line the two runs up bucket by bucket.

```scoutql
SELECT DATE_TRUNC('week', game_creation_at) AS week,
       COUNT(*) FILTER (WHERE win) AS wins,
       COUNT(*) FILTER (WHERE NOT win) AS losses
FROM match_participants
WHERE game_creation_at >= CURRENT_TIMESTAMP - INTERVAL 90 DAY
GROUP BY DATE_TRUNC('week', game_creation_at)
ORDER BY week ASC
RENDER stacked_bar WITH (y = (wins, losses), compare = previous_period)
```

`previous_period` is the only comparison in the language.

## The box-plot contract

A box plot takes its five numbers explicitly, and their **order in `y` is the
encoding**: minimum, first quartile, median, third quartile, maximum.

```scoutql
SELECT MIN(kills) AS low,
       QUANTILE_CONT(kills, 0.25) AS q1,
       MEDIAN(kills) AS med,
       QUANTILE_CONT(kills, 0.75) AS q3,
       MAX(kills) AS high
FROM match_participants
WHERE game_creation_at >= CURRENT_TIMESTAMP - INTERVAL 30 DAY
GROUP BY champion
ORDER BY med DESC
LIMIT 6
RENDER box_plot WITH (y = (low, q1, med, q3, high))
```

The names are yours; the positions are not. Nothing is inferred from what a
column is called, which is the same bargain the rest of the language makes —
`q3` could as easily be a 95th percentile, and only the query knows.
